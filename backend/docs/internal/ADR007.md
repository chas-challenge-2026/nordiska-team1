# ADR 0007: Multi-Module Database Context Strategy

## Status

Accepted

## Context

The v2 backend is structured as a modular monolith with separate business modules for Banking, Reporting, FAQ, and Inbox. Each module manages its own domain entities and database schema.

Entity Framework Core (EF Core) is used as the Object-Relational Mapping (ORM) layer. EF Core requires a DbContext class to manage database access for a set of entities.

The system must decide how DbContext instances are organized relative to module boundaries and how database transactions are scoped.

## Decision

The v2 backend uses a separate DbContext per module, aligned with PostgreSQL schemas and module boundaries.

### DbContext per Module

Each module defines its own DbContext:

- `BankingDbContext` for the Banking module (schema: banking)
- `ReportingDbContext` for the Reporting module (schema: reporting)
- `FaqDbContext` for the FAQ module (schema: faq)
- `InboxDbContext` for the Inbox module (schema: inbox)

Each DbContext maps to a single PostgreSQL schema using `HasDefaultSchema()` in the `OnModelCreating` method.

### Separate Connection Strings

Each module can use a different connection string if needed, although in practice most modules share the same database server and credentials.

The Frontend API is configured with connection strings for all modules:

- `ConnectionStrings:DefaultConnection`
- `ConnectionStrings:BankingDatabase`
- `ConnectionStrings:FaqDatabase`
- `ConnectionStrings:ReportingDatabase`
- `ConnectionStrings:InboxDatabase`

The Reporting Worker only requires `ConnectionStrings:ReportingDatabase` because it operates exclusively within the Reporting module.

This separation enforces least privilege at the configuration level. The worker cannot access Banking or FAQ data even if the code attempted to do so.

### Transaction Scope

Database transactions are scoped to a single DbContext and therefore a single module.

A use case that modifies data in multiple modules must coordinate across separate transactions. This is acceptable because module boundaries are designed to avoid the need for distributed transactions.

If a cross-module workflow is required, it is modeled as separate operations with compensating actions if one step fails.

### Migrations per Module

Each module manages its own EF Core migrations. Migrations are stored in the module's Infrastructure layer:

- `Banking/Infrastructure/Db/Migrations/`
- `Reporting/Infrastructure/Db/Migrations/`
- `FAQ/Infrastructure/Db/Migrations/`
- `Inbox/Infrastructure/Db/Migrations/`

A shared migration runner applies all module migrations in sequence during deployment. The migration connection string uses the `nordiska_migrator` role with DDL privileges.

### Dependency Injection Registration

Each module provides a registration method for its DbContext. For example:

```csharp
services.AddModulePostgresDbContext<BankingDbContext>(
    configuration,
    BankingDatabase.Details);
```

The shared `AddModulePostgresDbContext` helper configures the DbContext with:

- Connection string from configuration
- PostgreSQL provider (Npgsql)
- Schema name
- Connection pooling
- Sensitive data logging (disabled in production)

This ensures consistent configuration across modules while allowing each module to manage its own DbContext.

### Testing Strategy

For unit and integration tests, EF Core's InMemory provider is used instead of PostgreSQL.

The InMemory provider allows fast, isolated tests without requiring Docker or a running database. It provides sufficient fidelity for most business logic tests.

For tests that require PostgreSQL-specific behavior (triggers, constraints, complex queries), a real PostgreSQL instance is used. However, most tests use InMemory for speed and simplicity.

Tests configure each module's DbContext independently. This ensures that module boundaries are respected even in test scenarios.

## Rationale

### Why separate DbContext per module

Each DbContext represents a bounded context in Domain-Driven Design terms. Separating contexts by module enforces boundaries and prevents unintended coupling.

If all entities were in a single DbContext, developers could accidentally query across module boundaries without going through defined contracts. Separate contexts make violations explicit and easier to detect in code review.

Separate contexts also improve testing. A test can instantiate only the DbContext it needs without loading unrelated entities.

### Why separate connection strings

Separate connection strings allow different modules to use different database roles or even different database servers if needed in the future.

For example, the Reporting Worker can be configured with a read-only connection string for Banking data, enforcing least privilege at the database level.

In practice, most modules share a connection string, but the separation provides flexibility for future security hardening.

### Why module-local transactions instead of distributed transactions

Distributed transactions (two-phase commit) across multiple databases are complex, slow, and fragile. They require coordination protocols (XA, DTC) and introduce failure modes that are difficult to test and recover from.

The modular monolith architecture avoids distributed transactions by designing module boundaries such that most use cases operate within a single module.

In rare cases where cross-module coordination is needed, it is modeled explicitly with eventual consistency and compensating actions. This is more robust and maintainable than relying on distributed transactions.

### Why EF Core InMemory for tests instead of TestContainers

EF Core InMemory is faster and simpler for most tests. Tests run in milliseconds instead of seconds.

InMemory does not support all PostgreSQL features (triggers, constraints, full-text search), but most business logic does not depend on these features directly.

For the small number of tests that require PostgreSQL-specific behavior, a real database can be used. But the majority of tests benefit from the speed of InMemory.

TestContainers would add Docker as a dependency for running tests. This increases setup complexity and CI/CD build time. InMemory avoids this cost.

## Alternatives

### Alternative 1: Separate DbContext per module with module-local transactions (selected)

Enforces module boundaries, simplifies testing, avoids distributed transactions.

### Alternative 2: Single DbContext for all entities

**Advantages:** Simpler configuration. All entities in one place. Easier cross-module queries.

**Disadvantages:** Violates module boundaries. Risk of unintended coupling. Harder to enforce least privilege. All modules must share the same connection string and database role.

**Rejected because it weakens separation of concerns.**

### Alternative 3: Separate database per module

**Advantages:** Strongest possible isolation. Each module could use a different database server.

**Disadvantages:** Requires distributed transactions for cross-module workflows. Higher operational complexity. More connection overhead. Schema management is more complex.

**Rejected because schema-level separation is sufficient for a modular monolith. Full database separation would require microservices-level infrastructure.**

### Alternative 4: DbContext per aggregate root

Some DDD practitioners recommend one DbContext per aggregate root for the finest-grained isolation.

**Advantages:** Maximum isolation. Very clear boundaries.

**Disadvantages:** Excessive number of contexts for this system. Increased configuration overhead. Harder to manage migrations. Diminishing returns on isolation benefit.

**Rejected because module-level granularity is sufficient.**

### Alternative 5: Use Dapper or raw ADO.NET instead of EF Core

**Advantages:** More control over SQL. Potentially better performance for read-heavy workloads.

**Disadvantages:** Loses type safety. More boilerplate code. Manual mapping between database and entities. No migrations framework.

**Rejected because EF Core provides a good balance of productivity and performance for this system.**

## Risk-Driven Decisions

### Risk: Developer accidentally queries across module boundaries

**Mitigation:** Separate DbContexts make cross-module queries impossible without explicitly referencing another module's DbContext. Code review catches such violations.

### Risk: Module requires data from another module and cannot query it directly

**Mitigation:** Modules communicate through defined service interfaces and contracts. If Module A needs data from Module B, it calls a service method provided by Module B. This is intentional design to enforce boundaries.

### Risk: InMemory tests do not catch PostgreSQL-specific bugs

**Mitigation:** Accept this risk for most tests. Use real PostgreSQL for critical tests that depend on database-specific behavior (triggers, constraints). CI/CD can run integration tests against PostgreSQL to catch issues before production.

### Risk: Connection string misconfiguration allows unintended database access

**Mitigation:** Configuration validation at startup. If a required connection string is missing, the application fails fast. Least-privilege database roles limit impact of misconfiguration.

### Risk: Migration conflicts if multiple modules modify the same table

**Mitigation:** Each module owns its schema. Tables are not shared across schemas. If cross-module data sharing is needed, it is done through service calls, not direct table access.

## Consequences

### Positive

- Clear module boundaries enforced at the database level
- Each module manages its own migrations independently
- Least privilege is easier to enforce with separate connection strings
- Testing is simpler because contexts can be instantiated independently
- Transactions are simple and module-local (no distributed transaction complexity)
- Horizontal scaling is easier (modules could be separated into microservices in the future)

### Negative

- More boilerplate for DbContext registration and configuration
- Cross-module data access requires explicit service calls (cannot just join tables)
- Migration runner must apply migrations for all modules in sequence
- InMemory tests do not catch all PostgreSQL-specific issues
- Developers must understand which DbContext to use for each entity

## Result

The v2 backend uses a separate EF Core DbContext per module, each mapped to a PostgreSQL schema and configured with its own connection string.

Transactions are scoped to a single module. Cross-module workflows are modeled with eventual consistency and compensating actions.

Each module manages its own migrations. Tests use EF Core InMemory for speed and simplicity.

This design enforces module boundaries, simplifies testing, and avoids the complexity of distributed transactions while maintaining the flexibility to separate modules into independent services in the future.
