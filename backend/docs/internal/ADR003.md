# ADR 0003: Native C++ PDF Integration via P/Invoke

## Status

Accepted

## Context

The v2 backend requires the ability to generate PDF documents for tax reports and account statements. These documents must be generated efficiently and include complex formatting, calculations, and optional cryptographic signatures.

A native C++ library has been developed by the native team that provides high-performance PDF generation.

The .NET backend needs to integrate with this native library to enable report generation. This integration needs to adress the following risks:

\* Breaking least privilege

\* Stopping the API-service if PDF-generation breaks

\* Mishandling/Incorrectly implementing unmanaged calls to Native code

## Decision

The .NET Reporting Worker integrates with the native C++ PDF generator library using Platform Invoke (P/Invoke) with a C ABI boundary for PDF generation. Optional document signing is handled by a separate signing service.

To adress the three largest risks we have decided to write the PDF-reporter logic in its own module, completely seperated from the API module. The native calls are written with a managed wrapper. The module will in turn also have its own database role. 

## Rationale

This adresses all the key concerns we and the Native-team has. Seperating the modules means that the Worker runs its own process and has no direct communication with the API. The database role has limited access. The API reporting module would generate all the metadata needed to make a PDF and add that to the database.

The Worker-module only fetches this pre-prepeared data from assigned tables, which means that the module has no access to sensetive “core”-tables such as Accounts and Transactions. In summary  the two modules communicates indirectly via the database. 

An additonal “win” is also that we can work on this module at the same time as the API-module without breaking anything during development, since there is no direct dependencies between each process. 

## Alternatives

### Alternative 1: Seperated process in a Worker-module (selected)

**Advantages:** Keeps least privilege, more scalable and easier to maintain since its seperated from the API. 

**Disadvantages:** Harded to develop, will take atleast 3x more time. More testing will be required.

### Alternative 2: Worker inside the API-module

**Advantages:** Quick solution

**Disadvantages:** Breaks least privilege, risks breaking the application during runtime, makes role-based access control much harder to maintain, couples unrelated parts of the application making it less scalable for further maintanence



## Consequences

### Positive

- High-performance PDF generation without network overhead

- Customer data never leaves worker process (stays in-process memory)

- Simple deployment for PDF generation 

- Scalable and robust security. It is clear what data the worker has access too.

- Less development conflicts due to seperation

### Negative

- Complexity is higher

## Result

The Reporting Worker integrates sucessfully with the native C++ PDF generator library using P/Invoke with a stable C ABI and callback-based result handling for in-process PDF generation.

Optional document signing is handled by a separate signing service that communicates via Unix domain socket and receives only SHA-256 hashes, never customer data.

This architecture provides high performance and strong customer data protection while maintaining clear boundaries between PDF generation and cryptographic key operations.

The integration has been tested on both Windows and Linux and is in active use for generating tax reports and account statements, with optional CMS signatures and RFC 3161 timestamps.
