# ADR 0005: Authentication and Authorization Strategy

## Status

Accepted

## Context

The v2 backend serves multiple types of users with different security requirements:

- Retail customers accessing their accounts via web portal
- Internal staff members managing customer support cases
- Administrative users with elevated privileges

The system must authenticate users securely, maintain session state, and enforce fine-grained authorization rules based on user roles and resource ownership.

Swedish banking regulations require strong authentication for certain operations, particularly those involving external transfers of funds.

## Decision

The v2 backend implements a layered authentication and authorization strategy:

1. BankID integration for customer authentication
2. Username and password authentication for staff and admin users
3. JWT Bearer tokens stored in HttpOnly cookies for session management
4. Role-Based Access Control (RBAC) for coarse-grained permissions
5. Resource-based authorization for fine-grained access control
6. Step-up authentication with BankID for high-risk operations

### BankID Integration

Customer authentication uses the official Swedish BankID e-identification service through the ActiveLogin.Authentication.BankId.AspNetCore library.

BankID provides strong, government-approved authentication linked to the customer's Swedish personal identity number (personnummer).

The authentication flow:

1. Customer initiates login
2. Backend generates BankID authentication request
3. Customer completes BankID authentication on mobile device
4. Backend receives BankID completion callback
5. Backend verifies BankID signature and extracts user identity
6. Backend issues JWT token for authenticated session

For development and testing, the BankID simulated environment is used. Production uses the official BankID test or production environment.

### Username and Password for Staff

Internal staff and admin users authenticate with email and password.

Passwords are hashed using BCrypt with a work factor of 12. The BCrypt.Net-Next library is used for implementation.

Staff accounts are managed separately from customer accounts and stored in the StaffMember entity.

Account lockout is enforced after 5 failed login attempts. Locked accounts are automatically unlocked after 15 minutes or can be unlocked by an administrator.

### JWT Bearer Tokens in HttpOnly Cookies

After successful authentication, the backend issues a JWT Bearer token containing:

- User ID
- User type (Customer, Staff, Admin)
- Role claims
- Token expiration

The token is returned to the client as an HttpOnly cookie. HttpOnly prevents JavaScript from reading the token, mitigating XSS attack risk.

The cookie also has the Secure flag (HTTPS only) and SameSite=Strict to prevent CSRF attacks.

### Token Lifetime and Refresh

JWT tokens have a 15-minute lifetime.

A short lifetime limits the window of opportunity if a token is stolen. However, requiring re-authentication every 15 minutes would be disruptive to user experience.

To balance security and usability, the backend provides a token refresh endpoint. If the user is active and the refresh request is made before the token expires, a new token is issued.

The refresh mechanism allows sessions to continue seamlessly while maintaining a short token lifetime.

If the token expires without refresh, the user must re-authenticate.

### Role-Based Access Control

Three primary roles are defined:

- **Customer**: Retail banking customers
- **Staff**: Internal support and operations personnel
- **Admin**: System administrators with elevated privileges

Authorization policies check role claims in the JWT token. Controllers and endpoints use `[Authorize(Roles = "...")]` attributes to enforce access control.

### Resource-Based Authorization

In addition to role checks, the system enforces resource ownership rules.

For example, a customer can only view their own accounts and transactions. The authorization logic verifies that the requested resource belongs to the authenticated user.

Staff and admin users may have broader access depending on their role and department.

### Step-Up Authentication for High-Risk Operations

External transfers (transfers to accounts outside the bank) require additional authentication with BankID, even if the user is already authenticated.

This provides a second factor of verification for irreversible operations where funds leave the bank's control.

The user must complete a fresh BankID authentication transaction linked to the transfer request. The backend verifies the BankID signature and the user identity before processing the transfer.

### Rate Limiting

To prevent brute-force attacks and abuse, rate limiting is applied to authentication endpoints:

- Login endpoints: 10 requests per 60 seconds per IP address
- Transaction endpoints: 10 requests per 60 seconds per user with sliding window and segments

Rate limits are enforced using ASP.NET Core rate limiting middleware.

## Rationale

### Why BankID for customer authentication

BankID is the de facto standard for strong authentication in Sweden. It is widely adopted, government-approved, and provides legal non-repudiation for sensitive transactions.

Using BankID allows the bank to meet regulatory requirements for strong customer authentication without implementing custom two-factor authentication.

### Why JWT tokens instead of session cookies

JWT tokens are stateless. The backend does not need to store session state in a database or cache.

This simplifies horizontal scaling. Any backend instance can validate a token without coordinating with a central session store.

JWT tokens also carry claims, reducing the need for database lookups on every request.

### Why HttpOnly cookies instead of localStorage

Storing tokens in browser localStorage makes them accessible to JavaScript, including any JavaScript injected by an XSS attack.

HttpOnly cookies cannot be read by JavaScript. Even if an XSS vulnerability exists, the attacker cannot steal the token through client-side code.

The cookie-based approach provides defense-in-depth against XSS.

### Why 15-minute token lifetime

A short token lifetime limits the impact of token theft. If an attacker intercepts a token, they can only use it for 15 minutes before it expires.

The tradeoff is that shorter lifetimes require more frequent refreshes. 15 minutes is a balance between security and user experience.

Users who remain active will refresh tokens automatically. Users who leave their session idle for more than 15 minutes must re-authenticate, which is acceptable from a security perspective.

### Why step-up authentication for external transfers

External transfers are irreversible. Once funds are sent to an account outside the bank, they cannot be recalled.

Requiring BankID for these operations provides an additional safeguard. Even if an attacker compromises the user's session token, they cannot initiate an external transfer without also compromising the user's BankID (which requires physical access to the user's mobile device).

This aligns with regulatory requirements for strong authentication on high-risk transactions.

## Alternatives

### Alternative 1: BankID + JWT in HttpOnly cookies with RBAC and step-up (selected)

Provides strong authentication, stateless scalable sessions, XSS protection, and regulatory compliance.

### Alternative 2: Username and password only for all users

**Advantages:** Simpler implementation, no dependency on external BankID service.

**Disadvantages:** Does not meet regulatory requirements for strong authentication. Higher risk of credential compromise. Not acceptable for production banking system.

**Rejected.**

### Alternative 3: JWT tokens in localStorage

**Advantages:** Easier to access from JavaScript in single-page application.

**Disadvantages:** Vulnerable to XSS token theft. Tokens can be exfiltrated by malicious scripts.

**Rejected due to security risk.**

### Alternative 4: Server-side session state with session cookies

**Advantages:** More control over session invalidation. No token expiration refresh complexity.

**Disadvantages:** Requires centralized session store (Redis, database). Adds latency and complexity. Harder to scale horizontally. Session store becomes a single point of failure.

**Rejected because stateless JWT approach is simpler and more scalable.**

### Alternative 5: OAuth 2.0 / OpenID Connect with external identity provider

**Advantages:** Offloads authentication to specialized provider. Standards-based.

**Disadvantages:** Adds external dependency. Regulatory compliance would need to be verified for third-party provider. BankID is already the Swedish standard.

**Rejected because BankID integration is direct and meets all requirements.**

## Risk-Driven Decisions

### Risk: Weak authentication allows unauthorized account access

**Mitigation:** BankID provides government-approved strong authentication for customers. Password policies and BCrypt enforce strong credentials for staff. Account lockout limits brute-force attempts.

### Risk: Stolen JWT token allows prolonged unauthorized access

**Mitigation:** 15-minute token lifetime limits exposure window. HttpOnly cookies prevent XSS token theft. Secure and SameSite flags prevent CSRF and downgrade attacks.

### Risk: Attacker initiates fraudulent external transfer

**Mitigation:** Step-up authentication with BankID required for all external transfers. Even with stolen session token, attacker cannot complete transfer without BankID access.

### Risk: Brute-force password attacks on staff accounts

**Mitigation:** Rate limiting on login endpoints (10 attempts per 60 seconds). Account lockout after 5 failed attempts. BCrypt work factor makes password cracking computationally expensive.

### Risk: Customer cannot log in due to BankID service outage

**Mitigation:** Accept this risk. BankID is a highly available national service. Fallback to weaker authentication would compromise security. Operational procedures include monitoring BankID availability and communicating outages to customers.

### Risk: Session fixation or session hijacking attacks

**Mitigation:** JWT tokens are securely generated and signed. Tokens include expiration and issuer validation. SameSite=Strict prevents CSRF-based token injection.

## Consequences

### Positive

- Strong regulatory-compliant authentication with BankID
- Stateless and horizontally scalable session management
- XSS-resistant token storage via HttpOnly cookies
- Fine-grained access control with RBAC and resource ownership
- High-risk operations protected by step-up authentication
- Rate limiting prevents brute-force and abuse
- Clear separation between customer and staff authentication

### Negative

- Dependency on external BankID service for customer authentication
- Token refresh adds complexity to client and server interaction
- Short token lifetime requires active session management
- HttpOnly cookies require same-origin requests or CORS configuration
- Step-up authentication adds friction to external transfers

## Result

The v2 backend uses BankID for customer authentication, username/password for staff, and JWT Bearer tokens in HttpOnly cookies for session management.

Role-Based Access Control enforces coarse-grained permissions. Resource-based authorization enforces ownership checks. External transfers require step-up BankID authentication.

This design meets regulatory requirements for strong authentication while providing a secure and scalable authorization model.
