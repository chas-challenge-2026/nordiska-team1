# ADR 0004: Immutable Ledger and Audit Trail Pattern

## Status

Accepted

## Context

A banking system must maintain a complete, tamper-proof record of all financial transactions. Regulatory requirements and accounting principles demand that transaction history cannot be altered or deleted after the fact.

Additionally, all security-critical events (authentication, authorization failures, configuration changes, admin actions) must be logged in a way that proves the log has not been modified.

Traditional approaches where records can be updated or deleted in place do not provide sufficient guarantees for financial and compliance use cases.

## Decision

The v2 backend implements an immutable ledger pattern for financial transactions and a cryptographically signed audit log for security events.

### Immutable Ledger for Financial Transactions

All financial transactions are recorded as immutable entries in a ledger table. The ledger is append-only. No transaction entry can be updated or deleted.

The ledger table structure:

- Each entry records a single account movement (debit or credit)
- Entries include timestamp, account, amount, transaction type, and reference
- Account balances are derived by summing ledger entries, not stored as mutable values
- Corrections are recorded as new offsetting entries, not modifications to existing entries

Database triggers enforce immutability by rejecting any DELETE or TRUNCATE operations on the ledger table.

### Account Balance Calculation

Account balances are calculated at query time:

```sql
SELECT SUM(amount) FROM ledger_entries WHERE account_id = ?
```

This ensures the balance always reflects the actual transaction history. There is no risk of desynchronization between a cached balance and the ledger.

For performance, balance queries can be optimized with database indexes and optional materialized views, but the ledger remains the source of truth.

### Soft Delete for Account Closure

When a customer closes an account, the account is marked as closed (soft delete) rather than removed from the database.

This preserves the referential integrity of historical ledger entries and allows account history to be retrieved even after closure.

Closed accounts are excluded from active account queries but remain available for reporting and audit purposes.

### HMAC-Signed Audit Log for Security Events

Security-critical events are logged in a separate audit table with HMAC-SHA256 signatures.

Each audit entry includes:

- Event type (login, authorization failure, admin action, etc.)
- Timestamp
- User identifier
- IP address
- Event details (JSON)
- HMAC signature computed over the entry contents

The HMAC key is stored securely (environment variable or secret manager) and is not part of the audit log itself.

The signature allows verification that an audit entry has not been modified. If an attacker attempts to alter an entry, the signature will no longer match.

Database triggers prevent deletion or modification of audit log entries.

### Why HMAC Instead of Append-Only Blockchain

HMAC signatures provide tamper evidence without the complexity and performance overhead of a blockchain structure.

For the use case of internal audit and compliance, HMAC is sufficient. Each entry is independently verifiable. A full blockchain would add significant write latency and storage overhead without meaningful additional security benefit in a centrally controlled database.

## Rationale

### Immutability enforces accounting correctness

In accounting, the principle of double-entry bookkeeping requires that all transactions are recorded and remain visible. Errors are corrected with offsetting entries, not by altering history.

The immutable ledger pattern directly models this principle in the database.

### Append-only ledger simplifies auditing and compliance

Auditors and regulators can review the complete transaction history without concern that records have been silently modified or deleted.

The system cannot hide past mistakes by editing the ledger. All corrections are explicit and traceable.

### Balance calculation from ledger prevents desynchronization

Storing account balances as separate mutable fields introduces the risk of desynchronization if a balance update fails or is skipped due to a bug.

Calculating balances from the ledger eliminates this risk. The balance is always consistent with the transaction history.

### HMAC signatures provide tamper evidence for audit logs

If an attacker gains write access to the database and attempts to modify audit logs to cover their tracks, the HMAC signature will fail verification.

This provides forensic evidence of tampering and makes silent log modification detectable.

## Alternatives

### Alternative 1: Immutable ledger with balance calculation and HMAC-signed audit log (selected)

Provides strong guarantees for financial correctness and audit integrity with acceptable performance characteristics.

### Alternative 2: Mutable transaction records with version history

Instead of an immutable ledger, allow updates to transaction records but keep previous versions in a history table.

**Advantages:** More flexible for corrections without creating offsetting entries.

**Disadvantages:** Violates accounting principles. More complex to audit. Risk of incomplete version tracking if history updates are missed.

**Rejected because it does not align with accounting standards.**

### Alternative 3: Cached account balances with eventual consistency

Store account balances as separate columns and update them asynchronously after ledger writes.

**Advantages:** Faster balance queries (no aggregation required).

**Disadvantages:** Risk of desynchronization. Adds complexity. Balance queries are already fast with proper indexing.

**Rejected because consistency risk outweighs performance gain.**

### Alternative 4: Blockchain-based audit log

Use a blockchain structure where each audit log entry includes a hash of the previous entry.

**Advantages:** Stronger tamper evidence. Provides a verifiable chain of custody.

**Disadvantages:** Higher write latency. More storage overhead. Requires sequential writes. Complex recovery if chain is broken.

**Rejected because HMAC provides sufficient tamper evidence for the use case without the performance cost.**

### Alternative 5: External audit log service

Send audit events to a separate append-only service (e.g., AWS CloudWatch Logs, third-party SIEM).

**Advantages:** Logs are outside the application database, harder for attacker to tamper with.

**Disadvantages:** Adds external dependency. Network failures can cause log loss. Higher operational cost.

**Rejected for now but may be considered for production deployments in the future.**

## Risk-Driven Decisions

### Risk: Financial records are modified or deleted to hide fraud or errors

**Mitigation:** Database triggers reject DELETE and UPDATE operations on ledger table. All corrections are recorded as new entries.

### Risk: Account balance desynchronizes from transaction history

**Mitigation:** Balances are calculated from ledger at query time. No separate balance field exists that can desynchronize.

### Risk: Audit logs are modified to hide unauthorized actions

**Mitigation:** Audit entries are signed with HMAC. Signature verification detects tampering. Database triggers prevent deletion.

### Risk: Ledger grows indefinitely and impacts query performance

**Mitigation:** Database indexes on account_id and timestamp. Queries filter by account or date range. Optional materialized views for aggregations. Archive old ledger entries to separate cold storage if needed in future.

### Risk: HMAC key is compromised and attacker can forge signatures

**Mitigation:** HMAC key is stored in secure environment configuration (Docker secrets, environment variables, secret manager). Key rotation procedure is defined. Access to key is restricted to API and worker processes only.

## Consequences

### Positive

- Complete and auditable financial transaction history
- Tamper-evident audit log for security events
- Account balances are always consistent with ledger
- Corrections are explicit and traceable
- Aligns with accounting and regulatory requirements
- Simple to implement with database triggers
- No risk of balance desynchronization

### Negative

- Ledger table grows continuously and cannot be pruned
- Balance queries require aggregation (mitigated with indexes)
- Corrections require offsetting entries instead of direct updates
- HMAC key management is an operational responsibility
- Database triggers must be tested and maintained
- Archive strategy will eventually be needed for very old entries

## Result

The v2 backend uses an immutable append-only ledger for all financial transactions and HMAC-signed audit logs for security events.

Database triggers enforce immutability. Account balances are calculated from ledger entries at query time. Corrections are recorded as new entries, not modifications.

This design provides strong guarantees for financial integrity and audit compliance while maintaining acceptable query performance.
