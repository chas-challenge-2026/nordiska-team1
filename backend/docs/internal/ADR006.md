# ADR 0006: Asynchronous Report Generation Architecture

## Status

Accepted

## Context

The v2 backend must generate financial reports (tax documents, account statements) for customers on demand. Report generation involves:

- Querying large volumes of transaction data
- Performing financial calculations
- Generating formatted PDF documents
- Optionally signing PDFs with cryptographic signatures
- Storing the generated documents for later retrieval

PDF generation can take several seconds to complete, especially for customers with long transaction histories. Generating reports synchronously within the HTTP request would block the user and risk request timeouts.

Additionally, if the native PDF generator or signing service experiences temporary issues, the system must be able to retry generation without requiring the user to resubmit the request.

## Decision

The v2 backend implements asynchronous report generation using a background worker pattern with a database-backed job queue.

### Architecture Overview

Report generation follows this flow:

1. Customer requests a report via the API
2. API creates a report job record in the database and returns a job ID to the customer
3. API responds immediately (job is queued, not yet generated)
4. A separate Reporting Worker process polls the database for pending jobs
5. Worker claims a job, generates the PDF using the native library, and updates the job status
6. Customer polls the API with the job ID to check status and download the PDF when ready

### Database-Backed Job Queue

Report jobs are stored in the `tax_report_jobs` and `account_statement_jobs` tables in the `reporting` schema.

Each job record includes:

- Job ID (GUID)
- Customer ID
- Request parameters (year, account, format, etc.)
- Job status (Pending, Processing, Completed, Failed)
- Leased timestamp (for worker coordination)
- Retry count
- Created and updated timestamps
- Error message (if failed)

The database serves as the durable job queue. Jobs persist across system restarts. No external message broker is required.

### Worker Polling and Job Leasing

The Reporting Worker is a separate .NET Hosted Service that runs continuously.

The worker polls the database every 30 seconds for jobs in Pending status.

When the worker finds a job, it claims the job by:

1. Updating the job status to Processing
2. Setting a lease timestamp (5 minutes)
3. Committing the transaction

The lease timestamp prevents multiple workers from processing the same job concurrently. If a worker crashes while processing a job, the lease expires after 5 minutes and another worker can claim it.

The worker processes up to 12 jobs concurrently (configurable). Each job runs on a separate thread from the thread pool.

### Retry Logic

If report generation fails due to a transient error (network timeout connecting to signing service, temporary file system issue), the worker marks the job as Pending and increments the retry count.

Jobs are retried up to 3 times with a 30-second delay between attempts.

If a job exceeds the maximum retry count, it is marked as Failed with an error message. The customer can view the error and resubmit the request if needed.

### Graceful Shutdown

When the worker receives a shutdown signal (SIGTERM), it stops accepting new jobs and allows in-progress jobs to complete.

The worker has a 25-second drain timeout. If jobs do not complete within this window, they are abandoned and the lease will expire, allowing another worker to retry them.

The Docker Compose configuration sets a 35-second stop grace period to allow the worker to drain cleanly.

### Status Tracking and User Experience

The customer can poll the job status endpoint to track report generation progress:

- **Pending**: Job is queued, waiting for worker
- **Processing**: Job is being generated
- **Completed**: PDF is ready for download
- **Failed**: Generation failed, error message available

The API returns appropriate HTTP status codes for each state. The frontend can show a progress indicator and automatically refresh until the job completes.

### Integration with Native PDF Generator

The worker loads the native C++ PDF generator library via P/Invoke. For each job, the worker:

1. Queries transaction data from the database
2. Transforms the data into JSON format expected by the native library
3. Calls the native PDF generation function
4. Receives the PDF data via callback
5. Writes the PDF to disk at a configured storage path
6. Updates the job record with the PDF file path and Completed status

The native library handles PDF formatting, layout, and optional signing. The worker is responsible for data preparation, orchestration, and persistence.

## Rationale

### Why asynchronous instead of synchronous

Generating PDFs synchronously would block the HTTP request for several seconds. This creates a poor user experience and risks request timeouts, especially for customers with many transactions.

Asynchronous generation allows the API to respond immediately. The customer receives a job ID and can poll for completion. The user is not blocked and can navigate away or continue using the portal while the report generates.

### Why database-backed queue instead of Redis or RabbitMQ

A database-backed queue simplifies deployment and operations. No additional infrastructure is required.

Job state is already stored in the database for status tracking. Using the database as the queue eliminates the need to synchronize state between a message broker and the database.

PostgreSQL provides sufficient performance for the expected job volume. If throughput becomes a bottleneck in the future, the design can migrate to a dedicated message broker without changing the API contract.

### Why polling instead of push notifications

PostgreSQL LISTEN/NOTIFY could be used to push job notifications to workers instead of polling.

Polling was chosen for simplicity. A 30-second poll interval is acceptable latency for report generation. Polling is easier to reason about, test, and troubleshoot than notification-based coordination.

If latency requirements tighten, the design can be extended to support NOTIFY without changing the job model.

### Why job leasing instead of SELECT FOR UPDATE

Job leasing with timestamps allows multiple workers to coordinate without holding long-lived database locks.

SELECT FOR UPDATE would lock rows during PDF generation, which can take several seconds. This could lead to lock contention and reduced concurrency.

Lease-based coordination allows workers to claim jobs with a short transaction and then process them independently. If a worker crashes, the lease expires and the job becomes available for retry.

### Why Hosted Services instead of Hangfire or Quartz

Hosted Services are built into .NET and require no additional dependencies.

The job scheduling requirements are simple (poll for pending jobs, process concurrently, retry on failure). A dedicated job framework like Hangfire or Quartz would add complexity and a learning curve without providing significant additional value for this use case.

If more complex scheduling is needed in the future (scheduled reports, recurring jobs, job chaining), the design can migrate to a framework without changing the job model or API.

## Alternatives

### Alternative 1: Database-backed queue with polling worker and lease-based coordination (selected)

Simple, durable, and sufficient for expected load. No additional infrastructure required.

### Alternative 2: Redis or RabbitMQ message queue

**Advantages:** Higher throughput. Lower latency with push-based notifications. Dedicated queue infrastructure.

**Disadvantages:** Additional service to deploy, monitor, and manage. Queue state and database state can desynchronize. Operational complexity increases.

**Rejected because database-backed queue meets requirements with lower operational cost.**

### Alternative 3: Synchronous PDF generation in HTTP request

**Advantages:** Simpler code. No background worker. No job polling.

**Disadvantages:** Blocks user for seconds. Risks request timeouts. Cannot retry on transient failures. Poor user experience.

**Rejected due to user experience and reliability concerns.**

### Alternative 4: Azure Functions or AWS Lambda for serverless processing

**Advantages:** Automatic scaling. No worker process to manage.

**Disadvantages:** Requires cloud platform. Adds latency for cold starts. Native PDF library may not run in serverless environment without custom runtime. Increases deployment complexity.

**Rejected because the system runs on-premises or in Docker, not a cloud function platform.**

### Alternative 5: Hangfire or Quartz.NET for job scheduling

**Advantages:** Rich feature set. Web-based dashboard. Built-in retry and recurring jobs.

**Disadvantages:** Additional dependency and learning curve. More complexity than needed for simple polling and retry logic.

**Rejected because Hosted Services are sufficient for current requirements. Can migrate to a framework if scheduling needs grow.**

## Risk-Driven Decisions

### Risk: Worker crashes during PDF generation, job is lost

**Mitigation:** Jobs are persisted in the database before worker claims them. If worker crashes, job remains in database. Lease expires after 5 minutes and another worker can retry.

### Risk: Multiple workers process the same job concurrently

**Mitigation:** Job leasing with database transactions. Only one worker can successfully update a job to Processing. Other workers see the job is leased and skip it.

### Risk: Transient failures (network timeout, file system full) prevent job completion

**Mitigation:** Jobs are retried up to 3 times with 30-second delay. Transient errors are expected to resolve within the retry window.

### Risk: Database polling causes excessive load

**Mitigation:** 30-second poll interval is infrequent. Database queries are indexed on status and lease timestamp. Query cost is low. If load becomes an issue, consider PostgreSQL LISTEN/NOTIFY.

### Risk: Worker shutdown terminates in-progress jobs

**Mitigation:** Graceful shutdown with 25-second drain timeout. Docker stop grace period is 35 seconds. Workers finish current jobs before exiting. Abandoned jobs are retried when lease expires.

### Risk: Job queue grows indefinitely and fills database

**Mitigation:** Completed and failed jobs can be archived or purged based on retention policy. Define retention period (e.g., 90 days) and implement scheduled cleanup.

## Consequences

### Positive

- Non-blocking user experience for report requests
- Durable job queue survives restarts and failures
- Automatic retry for transient failures
- Graceful shutdown prevents job loss during deployment
- Horizontal scaling (multiple workers can run concurrently)
- Clear job status tracking for customers
- No additional infrastructure dependencies (Redis, RabbitMQ)
- Decouples API from PDF generation complexity

### Negative

- Jobs are eventually consistent (not instant)
- Polling introduces latency (up to 30 seconds before job is claimed)
- Requires customer to poll for job status (cannot push completion notification)
- Database-backed queue may not scale to millions of jobs per day (acceptable for current volume)
- Job cleanup and retention must be managed manually
- Worker process is an additional component to deploy and monitor

## Result

The v2 backend generates reports asynchronously using a database-backed job queue and a separate Reporting Worker process.

The worker polls for pending jobs, claims them with a lease-based coordination mechanism, generates PDFs using the native library, and updates job status.

Transient failures are retried automatically. Graceful shutdown ensures jobs complete during deployment.

This design provides a durable, scalable, and user-friendly report generation workflow without requiring additional message broker infrastructure.
