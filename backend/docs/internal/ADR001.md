# ADR 0001: Architecture and Transaction Pattern for v2

## Status

Accepted

## Context

The backend code in v1 is structured as a monolith where large parts of the logic are mixed together inside Razor Pages without a clear separation between domain logic, database access, and presentation concerns.

There is no consistent backend structure and no clear separation within the database. This makes the system difficult to extend, test, and secure. The current structure is also poorly suited for parallel development since multiple developers need to work in the same parts of the codebase.

For v2, the architecture therefore needs to:

- support parallel development in a larger team,
- provide clear areas of responsibility,
- enable least privilege in the database,
- reduce coupling between features,
- remain simple to run and deploy,
- and support future growth through additional features and executable processes.

## Decision

### Modular monolith with a Clean Architecture-inspired structure

The backend will be built as a **modular monolith**, where the system is divided according to the application's main areas of responsibility.

The system initially consists of the following business modules:

- Banking
- Reporting
- FAQ
- Inbox

Each module is implemented as a separate library and is primarily organized into:

- **Domain** – domain models and business rules.
- **Application** – use cases, services, interfaces, and application logic.
- **Infrastructure** – implementations for database access and external dependencies.

Shared database infrastructure is handled separately from the business modules.

The system initially contains two executable applications:

1. **Frontend API** – handles HTTP requests from the frontend and uses the relevant business modules.
2. **Reporting Worker** – handles background processing, primarily report and PDF generation.

Additional modules and executable processes can be added without changing the overall system structure. For example, a separate API process for a mobile application could be introduced later.

### The database follows module boundaries

The database is divided into separate PostgreSQL schemas based on the responsibilities of each module, for example:

- `banking`
- `reporting`
- `faq`
- `inbox`

This makes module boundaries explicit at the database level as well.

Executable processes use separate database roles with only the permissions required by that process. A worker therefore does not automatically receive the same database permissions as the API.

This is used to enforce **least privilege** and reduce the potential impact if an individual process is compromised.

### Communication between modules

Modules should, as far as possible, communicate through defined interfaces and contracts instead of directly depending on another module's internal implementation.

A module should therefore not depend on how another module internally stores or processes its data.

As long as the contract's input and output remain compatible, the underlying implementation can change without requiring changes in its consumers.

This reduces coupling and makes it easier for multiple team members to work on different parts of the system in parallel.

### Transaction pattern

A transaction should normally be limited to a single use case and the module that owns the affected data.

Database operations that together represent one atomic change are executed within the same database transaction. Either the entire change succeeds, or the transaction is rolled back.

We avoid designing business logic that depends on long-running transactions spanning multiple modules.

When work needs to continue outside the original request flow, for example PDF report generation, the state of that work is first persisted in the database. The worker can then process the work independently.

The database therefore acts as the durable boundary between the synchronous API flow and asynchronous background processing.

Example:

`API request → database transaction → report job persisted → commit → worker claims job → PDF generated → result persisted`

This means that a failure during PDF generation does not need to roll back the user's original request. Instead, the job can be marked as failed and later retried or recovered.

## Rationale

The chosen architecture provides several important advantages:

1. **Clear and scalable structure**

   New functionality can be added to existing or new modules without requiring a redesign of the entire backend. A consistent structure also makes the codebase easier for new developers to understand.

2. **Least privilege becomes easier to enforce**

   When both the application and database are divided according to areas of responsibility, processes and database roles can be restricted to only the information they actually need.

3. **Reduced coupling between different parts of the system**

   Modules communicate through clear contracts instead of depending on each other's internal implementations.

4. **Better support for parallel development**

   Team members can work in different modules with a lower risk of conflicts and unintended dependencies.

5. **Simpler operations than microservices**

   The system gains many of the benefits of clear service boundaries without introducing the network communication, deployment complexity, and observability infrastructure required by a microservice architecture.

## Alternatives

### Alternative 1 – Modular monolith — selected

The system is divided into clear business modules while still being built, tested, and deployed as a cohesive system.

This provides a good balance between separation and operational simplicity for the size of the project.

### Alternative 2 – Microservices

Each business area could instead have been implemented and deployed as a separate service.

This would provide stronger physical isolation and allow services to scale independently, but would also require significantly more infrastructure for areas such as:

- network communication,
- service discovery,
- authentication between services,
- failure handling,
- distributed transactions,
- logging and tracing,
- deployment and version management.

For the size and needs of this project, the additional complexity is not considered justified.

### Alternative 3 – Traditional layered monolith

The backend could instead have been divided globally into layers such as:

`Controllers → Services → Repositories → Database`

This would be simple to implement initially.

The disadvantage is that the system would primarily be divided by technical layers instead of business responsibilities. As the system grows, all controllers, services, and repositories risk being grouped together even though they belong to completely different areas of the application.

This makes module ownership, boundaries, and database permissions less explicit, and the approach was therefore rejected.

## Risk-driven decisions

The architectural decisions are based on risks identified for the project.

### Risk: A compromised component gains access to the entire database

**Mitigation:**  
The database is divided into schemas, and separate database roles are used for different processes. Each process is granted only the permissions it requires.

### Risk: Excessive coupling between different parts of the backend

**Mitigation:**  
The system is divided by business responsibility, and communication occurs through defined interfaces and contracts.

### Risk: Multiple developers modify the same code simultaneously

**Mitigation:**  
Module boundaries create clearer areas of ownership and allow development to happen more independently.

### Risk: A failure in background processing affects the user's original operation

**Mitigation:**  
Long-running operations, such as PDF generation, are executed outside the HTTP request by a separate worker. The job state is persisted before processing begins.

### Risk: Partially completed database operations create inconsistent data

**Mitigation:**  
Operations that together form a single use case are executed atomically within a database transaction.

### Risk: The architecture becomes unnecessarily complex for the size of the project

**Mitigation:**  
A modular monolith is used instead of microservices. Module boundaries exist in both the codebase and database without requiring every module to become a separate network service.

## Consequences

### Positive

- Clearer responsibility between business areas.
- Easier parallel development.
- Easier enforcement of least privilege.
- Reduced coupling between different parts of the system.
- Modules can be tested more independently.
- New modules can be added without major architectural changes.
- Background work can be executed separately from the API process.
- Simpler deployment and troubleshooting compared to a microservice architecture.
- Individual modules or workflows can later be extracted into separate services if needed.

### Negative

- The architecture requires discipline to ensure that module boundaries are maintained.
- Since multiple modules use the same database server, the system does not provide the same level of physical isolation as separate microservices.
- Interfaces and abstractions introduce slightly more code than a small traditional monolith.
- Changes affecting multiple modules may require coordination between their contracts.
- Asynchronous processing means that some workflows become eventually consistent instead of being completed within a single transaction.

## Result

The architecture gives v2 clear business and security boundaries while keeping the system simple to operate as a whole.

Module boundaries exist both in the application code and in the database. This means that the structure is useful not only for organizing code, but also as a foundation for security controls and least privilege.

If the system's requirements change in the future, individual modules or workflows can be separated into their own processes or services without requiring a complete redesign of the backend.
