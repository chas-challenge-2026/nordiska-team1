# ADR 0002: Database architecture & security modelling for v2

## Status

Accepted

## Context

The v2 backend requires a database architecture that supports modular growth while enforcing secure and controlled access to data.

The database must also support a development workflow where developers can initialize and update the database without manually managing credentials or bypassing security practices.

## Decision

PostgreSQL will be used with:

- Separate database schemas aligned with backend modules.
- Role-Based Access Control (RBAC).
- Separate database roles for:
    - API
    - Reporting Worker
    - Database migrations
- Least-privilege permissions for each role.
- Separate permission definitions for development and production environments.

The API and Worker roles only receive access to the schemas, tables and operations required for their responsibilities. Additional roles may be introduced as the system grows.

Database migrations are executed using a dedicated migration role with elevated schema-management permissions. Application services do not receive migration privileges.

For development, a DevTools executable is responsible for initializing the local database environment. It generates secure database credentials, stores them in protected `.gitignored` environment files and configures the corresponding .NET User Secrets.

This provides developers with a consistent database setup while reducing the risk of credentials being committed to source control.

## Rationale

Separating the database into schemas matching application modules creates clear ownership boundaries and makes least-privilege access easier to enforce.

Separating runtime roles from migration privileges limits the impact of a compromised application process.

Automating development credential management reduces manual configuration, accidental secret exposure and differences between developer environments.

## Alternatives

### Alternative 1 – PostgreSQL with a single application role

Simpler to configure, but gives all backend components access to more data and operations than necessary.

Rejected because it weakens isolation and least-privilege enforcement.

### Alternative 2 – Separate database per module

Provides stronger isolation but introduces additional operational complexity, connection management and migration overhead.

Rejected for the current system because schema-level isolation provides sufficient separation while keeping the modular monolith simple.

### Alternative 3 – Manually managed development credentials

Developers manually create database users, passwords and environment variables.

Rejected because configuration becomes inconsistent and increases the risk of weak or leaked credentials.

## Risk-driven decisions

- Application roles must not receive schema migration privileges.
- Worker access is restricted to reporting-related database resources required for its jobs.
- API access is restricted to resources required by API modules.
- Production permissions are stricter than development permissions.
- Secrets must not be stored in source control.
- Development credentials are generated rather than using shared static passwords.

## Consequences

### Positive

- Clear database ownership boundaries.
- Easier enforcement of least privilege.
- Reduced impact if an application service is compromised.
- Consistent and secure developer setup.
- Database roles and permissions can evolve independently as new services are introduced.
- Clear separation between runtime access and database administration.

### Negative

- More database roles and permission scripts must be maintained.
- Schema and permission changes require coordination when modules evolve.
- Development tooling becomes responsible for part of the local security configuration.

## Result

The v2 database uses PostgreSQL with module-aligned schemas and role-based least-privilege access.

Runtime services operate using restricted roles, migrations use a dedicated privileged role, and development database configuration is automated through DevTools to provide a consistent and secure development workflow.
