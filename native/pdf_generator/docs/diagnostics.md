# Diagnostic privacy boundary

The generator handles one customer per call. The host owns customer/job
correlation. Diagnostics identify the stage, schema field and document or
transaction position without returning supplied values.

```text
JSON -> ingestion -> layout -> rendering -> digest signer
            |           |          |             |
           typed failures: enum codes + numeric positions
                                 |
                    GeneratorError::diagnostic()
                                 |
                     format_diagnostic(Diagnostic)
                                 |
             C API thread-local text / typed CLI output
```

## Types and dependencies

`include/nordiska/diagnostics/diagnostic.hpp` defines the closed vocabulary:
`DiagnosticCode`, `DiagnosticStage`, `DiagnosticField`, and
`DiagnosticLocation`. Locations use a scope and optional zero-based document
and transaction positions generated by iteration. A field is an enum, never a
supplied JSON key or string path. Unknown input keys continue to be ignored.

Ingestion, layout, rendering and signing failures contain a subsystem kind,
code and typed location. Generator argument/internal failures also carry codes.
None stores strings, string views or text pointers. `GeneratorError` preserves
the variant for status classification and adds only a document position.

`nordiska_document_diagnostics` has no parser, renderer, service or host
dependency. `src/diagnostics/diagnostic.cpp` owns every diagnostic word.
`format_diagnostic` never receives JSON, domain objects, PDFs, exceptions, OS
messages or remote text. Unknown enum values use fixed fallback words. It
returns a private, NUL-terminated `DiagnosticText` using a 512-byte buffer
without allocation, including while reporting memory exhaustion. Maximum-size
positions and the longest reason fit within this capacity.

Examples:

```text
ingestion: documents[0].document.account_number: required
ingestion: documents[0].document.transactions[2].date: must be a string
signing: documents[1]: failed to connect to signer socket
delivery: delivery callback rejected batch
boundary: unexpected failure
```

`GeneratorError::message()` is a convenience wrapper around that formatter.
There is no second error message construction path.

## Output and exceptions

The core writes no application logs. The C ABI's sole error setter accepts a
`Diagnostic` and stores the formatter's bounded result in thread-local storage.
V1, V2 and both instrumented entry points share this path. Numeric status codes,
callback layouts, borrowed delivery ownership and atomic generation remain
compatible. Callback return values are never echoed.

Only `cli/output.cpp` writes application stdout/stderr. Its interface accepts
typed diagnostics, enum engine/ingestor choices and numeric statistics, never
arbitrary messages, filenames, customer objects or document identifiers. Help
and version output use fixed literals. Success JSON summaries use
`document_index` and `bytes`; `customer_id`, `document_id` and `file_path` are
removed. Consumers needing identity-bearing output should use the delivery API.
Completed PDF bytes and callback identifiers remain intentional artifact data.
The CLI still writes files to their requested destinations.

Parser exceptions become typed failures. Unexpected pipeline exceptions,
including custom signer exceptions, become `UnexpectedFailure`; `bad_alloc`
becomes `OutOfMemory`. Final ABI/CLI catch-all guards cover construction,
filesystem and callback failures. No handler reads `what()` or preserves
exception text in diagnostics. Signer extensions now receive only a 32-byte
digest and optional timing collector, with no customer or document context.
The external signer protocol is unchanged.

Internal C++ consumers/custom signers must migrate from free-text errors and
`SigningContext`. The public C ABI does not change.

## Verification and review

`nordiska_diagnostics_tests` checks both parsers, exact typed locations, all four
C entry points, atomic failure, callback rejection, throwing signers, memory
exhaustion, throwing callbacks, recovery after errors, reentrant callbacks,
maximum indices with every reason, and fallback vocabulary. Static assertions check
text-free failure types and reject string construction of diagnostics.

`nordiska_diagnostic_boundary_check` guards application source against common
output bypasses outside the CLI adapter and against `what()` access. It also
runs CLI processes with synthetic private markers across all renderers, both
parsers, normal/verbose/quiet/JSON modes, malformed JSON, unknown kinds,
duplicate IDs, usage failures, I/O failures and filesystem exceptions. Generated
artifacts must arrive while markers stay absent from both output streams.
The same check runs the real socket adapter against a mock protocol-v2 service,
covering connection failures, truncated/empty/oversized responses, private text
in invalid signature bytes, and every service error in plain and timestamp
modes. Requests must contain exactly the fixed header and 32-byte digest;
failed signing must never write a PDF. This validates the generator adapter,
not the external signer's TSA implementation or its independent output.

`nordiska_allocation_failure_tests` uses GNU linker wrapping in a separate test
executable, compiling the unchanged C ABI source with the core. It fails
successive C++ allocations in simdjson ingestion, each renderer, and all four
ABI paths through callback work, and verifies controlled errors and recovery.
The formatter is also exercised with all wrapped allocations disabled.
No test hook is added to production targets. These tests do not fault C-library
malloc, aligned/nothrow allocations, or every cold-start/third-party allocation.

This source guard supports review; it is not a general C++ information-flow
proof or a sandbox for arbitrary extension code.

Add failures by defining enum codes, fixed formatter reasons and typed
locations. Never add strings to failure types, general logging callbacks,
alternate setters, subsystem output or third-party text passthrough. Review the
vocabulary, formatter and output adapter together.

## Host and dependency scope

This covers the generator's own application diagnostics. It does not establish
a process-wide guarantee for .NET, the external signer or libraries that write
independent output. The .NET worker currently logs exceptions and persists their
messages. Its owner must replace arbitrary exception logging/persistence in
this flow with approved status/diagnostic fields and its own job reference.
Native diagnostics do not sanitize independent .NET or callback exceptions.
A complete audit must also verify library output and host crash reporting.

The optional nlohmann DOM backend has a known memory-exhaustion limit:
its noexcept destructor allocates a cleanup stack. Failure of that allocation
can terminate inside the dependency before our error boundary can run. Its
initial allocation failure is tested, but exhaustive DOM cleanup failure
recovery is not claimed. The production C ABI uses simdjson. Changing that
backend or guaranteeing process survival under total memory exhaustion needs
separate dependency work. This limit does not make customer text a permitted
diagnostic payload.
